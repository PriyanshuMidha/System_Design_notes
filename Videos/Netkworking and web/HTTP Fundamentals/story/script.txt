== s1 Level 1: the words
l1 | N | hook | This is Zoe. She opens a shopping app, and taps, my orders. Her phone has to ask a faraway computer for the list, and the computer has to answer. The two were built by different people, in different languages. H T T P is the shared set of rules that lets any app ask, and any server answer.
l2 | N | normal | Level one, the words. The client is the program that asks, a browser, or a Go H T T P client. The server is the program that answers. A request is one message from the client. A response is the server's reply to that one request.
l3 | N | normal | A header is a name and value line of extra information, like content type, application slash json. The body is the actual data carried by a message. A status code is a three digit number saying what happened. Four oh four means not found. And a cookie is a small value the browser stores, and sends back every time.
l4 | N | normal | Think of ordering at a restaurant counter. You say what you want, that is the method and the path. You add notes like, no onions, those are headers. And you get a tray back, with a receipt saying done, or sold out. That is the status code.
l5 | MAX | normal | I am Max, the counter clerk. And I forget you the moment you walk away. Every time, you must tell me everything again.
l6 | N | punch | Remember it like this. H T T P is asking with a method and a path, and being answered with a status code. And nothing is remembered between requests, unless a cookie or a token carries it.
== s2 Level 1: why a shared protocol exists
l7 | N | normal | Imagine every website invented its own private way of asking for a page, and its own private way of saying, found it, or not found. A browser built for one site could not talk to any other.
l8 | N | normal | Before H T T P, every service that served documents over a network invented its own protocol. H T T P, the hypertext transfer protocol, standardised the exchange into one shape. First defined in R F C nineteen forty five, now specified across R F C ninety one ten to ninety one fourteen. A browser from nineteen ninety six and a Go server written today still agree on what, get slash index dot H T M L, means.
l9 | N | normal | An example. A client calls post slash orders. It needs a way to say what kind of operation this is, create something. And the server needs a way to say what happened. Created, two oh one. Rejected, four hundred. The server broke, five hundred. All without the client learning a custom error format for every backend.
l10 | N | normal | So H T T P's whole job is to be a vocabulary every client and every server already agree on, so nobody invents their own.
== s3 Level 1: a letter and a receipt, and why forgetting is a feature
l11 | N | normal | The mental model. A request is a short, structured letter. The first line says what you want, and from where. A block of headers gives context. Who you are, which formats you accept, whether you already hold a cached copy. And an optional body carries data for the server to act on.
l12 | N | normal | The response mirrors it. A status line says what happened. Headers describe the reply. And an optional body carries the result.
l13 | N | normal | The clerk has no memory of you from your last visit. That is called statelessness, and it is part of the design, not an accident. Anything that must persist, a login, a shopping cart, has to ride along on every request, usually in a cookie or a token.
l14 | N | warn | A common mistake. Thinking the server remembers you because the connection stayed open. The T C P connection may persist, but H T T P itself carries no memory across requests. The server knows only what this exact request tells it.
l15 | N | normal | And that is the gift of statelessness. Every request is understandable on its own, so any server in a pool can answer any request.
== s4 Level 2: anatomy of a real exchange
l16 | N | normal | Level two. Here is a real exchange, measured against a local Go server with curl. The request says, get slash items slash one, H T T P one point one. Then a host header, a user agent header, and an accept header.
l17 | N | normal | The reply starts with a status line. H T T P one point one, two hundred, O K. Then headers. Cache control, max age sixty. Content type, application slash json. An E tag. A date. And content length, twenty six. Then a blank line, and the body, a small piece of J S O N.
l18 | N | normal | The arrows in curl's output show who said what. A greater than sign is what curl sent. A less than sign is what the server replied.
== s5 Level 2: methods, safe versus idempotent
l19 | N | normal | Now methods. Two separate promises hide behind every method's name. Safe means the method never changes server state, so a crawler, a prefetcher, or the back button can call it freely. Idempotent means calling it many times has the same effect on server state as calling it once.
l20 | PAT | normal | I am Pat, a crawler. I only ever ask safe questions. Get, head, options. I visit thousands of pages, and I never change anything.
l21 | N | normal | Here is the table. Get, head and options are safe, and idempotent. Put replaces a resource entirely, and delete removes it. Both are idempotent, but not safe. Post creates something, or triggers a side effect. It is neither, so a retry can create a duplicate. And patch is usually not idempotent.
l22 | N | warn | The trap hides in patch. Patch with status equals shipped is harmless to repeat. But patch with a relative change, decrement stock by one, runs twice and removes two. The method's name does not decide idempotency. The meaning of the operation does.
l23 | N | warn | And a classic mistake. Idempotent does not mean the response is identical every time. It means the end state is the same. A second delete of an item can return four oh four, instead of two oh four, and it is still idempotent, because the item is gone either way.
l24 | N | normal | This is why operations that must survive client retries, like creating a payment or placing an order, need an explicit idempotency key. The method alone is not enough.
== s6 Level 2: status codes
l25 | N | normal | Status codes fall into five families, by their first digit. Two hundreds mean success. Three hundreds mean redirection or not modified. Four hundreds mean the client did something wrong. Five hundreds mean the server broke. The family tells you who should act next.
l26 | N | normal | Now the pairs people mix up. Four oh one versus four oh three. Four oh one means you are not authenticated. Missing or invalid credentials. It says, log in. Four oh three means you are authenticated, but not authorised. I know who you are, and the answer is still no.
l27 | N | warn | Do not treat them as, logged in or not. A perfectly logged in user who hits an admin only route with a normal token gets four oh three, not four oh one. Their credentials are valid, just not enough.
l28 | N | normal | Four hundred versus four twenty two. Four hundred means the request is malformed. Broken J S O N, a wrong type, a missing field. Four twenty two means it was understood perfectly, but fails a business rule. An end date before a start date.
l29 | N | normal | Four oh nine, conflict, is about state. A version mismatch on optimistic locking. A duplicate unique key. It is about the current state of the server, not the shape of the request.
l30 | GIA | normal | I am Gia, a gateway runner. I carry requests between clients and upstream servers. When something goes wrong, I report it with one of three codes.
l31 | N | normal | Five oh two, bad gateway. The upstream answered, but badly, not in a valid shape. Five oh three, service unavailable. The server is temporarily unable, overloaded or in maintenance, often with a retry after header. And five oh four, gateway timeout. The upstream gave no response in time at all.
l32 | N | punch | Remember. Four oh one, I do not know who you are. Four oh three, I know exactly who you are, and the answer is still no.
== s7 Level 2: headers
l33 | N | normal | Headers are name and value metadata, riding next to the request line or status line. A handful appear in almost every real system.
l34 | N | normal | Host says which domain is asked for, mandatory since H T T P one point one. Content type is the media type of the body, J S O N, or multipart form data. Content length is the body size in bytes, so the receiver knows where the body ends. Authorization carries credentials, bearer token, or basic.
l35 | N | normal | Cache control carries caching directives, max age, no store, must revalidate. E tag, and if none match, are a fingerprint, and a conditional request. Set cookie, and cookie, are how the server asks the client to store a value, and how the client sends it back. And connection says keep alive, or close.
== s8 Level 2: conditional requests
l36 | N | normal | Conditional requests avoid resending what you already have. The server tags a representation with an E tag, a hash of its content. A client that has a copy sends, if none match, with that tag, on its next get.
l37 | MAX | normal | If nothing changed, I reply, three oh four, not modified. With no body at all.
l38 | N | normal | A two kilobyte J S O N is fetched once, in full. A minute later, the check costs a few bytes of headers, and nothing else. A three oh four is the server proving, nothing changed, cheaply. It is caching working, not failing. The full story is in the H T T P caching note.
== s9 Level 2: cookies
l39 | N | normal | How does state survive a stateless protocol? Cookies. A cookie is just a header the server asks the client to store, and resend on every later request. Its attributes decide how exposed it is.
l40 | N | normal | Secure means only sent over H T T P S. Without it, the session token can be sniffed on plain H T T P. Http only means not readable from JavaScript. A malicious script literally cannot read it, which blunts theft through cross site scripting.
l41 | N | normal | Same site controls whether the cookie is sent on cross site requests. Strict, lax, or none. It blunts cross site request forgery, by not attaching the session cookie to requests that started on another site. Domain says which hosts receive it, and too broad a domain leaks it to unrelated subdomains. Path scopes it, for example to slash admin only.
l42 | N | normal | A well set session cookie. Secure, http only, same site strict, path slash. Sent over H T T P S only, invisible to any script, and never attached to a request that started on another site.
l43 | N | warn | The mistake. Setting only http only, and assuming it is safe. It blocks scripts from reading the cookie. It does nothing against sniffing on plain H T T P, that needs secure. And nothing against a forged cross site request, that needs same site. Three attributes block three different attacks.
== s10 Level 2: keep-alive
l44 | N | normal | One more idea. H T T P one point oh opened a fresh T C P connection for every request. H T T P one point one defaults to keep alive, reusing one connection for several requests, avoiding a new handshake, and under T L S, a new T L S handshake, each time.
l45 | N | warn | But keep alive saves handshakes, not ordering. On one H T T P one connection, requests are still answered one at a time. That is why browsers open several connections per host, and why H T T P two multiplexing exists.
== s11 Level 2: a worked example, one PUT sent twice
l46 | N | normal | Let us trace one put, sent twice. First, put slash items slash forty two, with body v one. The store has no entry for forty two yet.
l47 | N | normal | The handler writes it. The store now holds forty two equals v one. It responds two oh one, created, because the resource did not exist before.
l48 | N | normal | The same put arrives again, as if the client retried after a timeout. The handler writes the same value. The store still holds exactly forty two equals v one. This time it responds two hundred, because the resource already existed.
l49 | N | punch | The responses differ, two oh one then two hundred. But the stored state after both calls is identical. That is what idempotent means, traced through real state.
== s12 Level 3: In Go, a tiny resource store
g1 | N | normal | Now the code, in Go. A tiny in memory store that shows method semantics. Get is safe. Put and delete are idempotent. Post is not.
g2 | N | normal | A store holds a mutex, a map from I D to value, and a counter. Handle get is safe. It looks up the item under the lock, and returns four oh four if missing.
g3 | N | normal | Then it computes the E tag, a hash of the body, and sets the E tag and cache control headers. If the request's if none match equals the tag, it writes three oh four and returns, with no body. Otherwise it writes the J S O N. It never changes state, so it can be cached, retried and prefetched freely.
g4 | N | normal | Handle put decodes the body, and answers four hundred if the J S O N is broken. It then writes the value under the lock. If the item existed, it replies two hundred, otherwise two oh one. Doing it twice leaves the same state, so it is idempotent.
g5 | N | normal | Handle delete removes the item, and always replies two oh four, whether or not it existed. Deleting twice still ends with it gone. And handle post creates a brand new item with a new I D every time, and counts how many it created. Retry it after a timeout, and you get a duplicate. That is why post is not idempotent. The tests prove each of these properties, with the race detector on.
== s13 Level 3: versions of HTTP
l50 | N | normal | A comparison. H T T P one point one is a plain text protocol, one request at a time per connection, easy to debug by hand. H T T P two keeps the same methods, status codes and headers, in multiplexed binary frames over one T C P connection. H T T P three keeps the same semantics again, over Quick streams, for lossy and mobile networks.
l51 | N | warn | An interview trap. Methods, status codes and headers are the same across all three. Only the wire format and connection model changed. Anyone who says H T T P two added new status codes has it backwards.
== s14 Level 3: deep dive
d1 | N | normal | Deeper points. First, why does four twenty two exist at all? The standard defines four hundred as any client error, which technically covers everything, from broken J S O N to a business rule. Four twenty two, borrowed from web dav, gives a separate signal for, understood, but invalid.
d2 | N | normal | Second, why safe methods matter beyond, do not delete things. Safety lets infrastructure the author never thought about, prefetchers, crawlers, C D Ns, retry logic in client libraries, treat get, head and options as free to issue speculatively. A get with a side effect breaks all of them.
d3 | N | normal | Third, idempotency is about end state, not about identical responses. The second delete may return four oh four, and the method is still idempotent. Confusing the two leads to rejecting correct designs.
d4 | N | normal | And last, content length versus chunked transfer. Content length needs the full body size before the first byte, which fails for a streamed response like a long export. Chunked transfer sends the body in pieces, each prefixed with its own size, ended by a zero length chunk. H T T P two and three replace it with their own framing.
== s15 Level 3: trade-offs, failures and what to watch
t1 | N | normal | Trade offs. Statelessness is a deliberate simplicity. Every request carries its own context, auth token, session cookie, which is overhead. But it is why any server in a pool can answer any request. Repeated text headers on every H T T P one request are wasteful, and H T T P two's header compression exists to fix that. And for chat or live updates, request response is the wrong shape. Use web sockets, server sent events, or long polling.
t2 | N | warn | Four production failures. A client treats four oh three as, please log in, and redirects to a login page. Wrong, because logging in again will not help. A non idempotent post is retried blindly by a client library on timeout, giving duplicate orders. Use an idempotency key.
t3 | N | warn | A get endpoint with a side effect, like mark as read on fetch. It breaks prefetching, crawling and caching, which all assume get is safe. And a session cookie missing secure or http only, so the token is stealable over plain H T T P, or through any script injection.
t4 | N | normal | What to watch. The status code distribution by class. A rising share of five hundreds is a server health signal. A rising share of four hundreds is often a client or contract problem. The three oh four hit rate on cacheable gets. And the rate of connection close, since frequent forced closes defeat keep alive.
== s16 Interview round
q0 | N | hook | Interview round. Seven questions you will really get.
q1 | N | normal | One. Safe versus idempotent? Safe never changes state, so get, head and options can be called freely. Idempotent means repeating has the same effect as once, but it can change state the first time. Put and delete are idempotent but not safe.
q2 | N | normal | Two. Four oh one versus four oh three? Four oh one, the request lacks valid credentials. Four oh three, the server knows who you are, and you are not allowed. A valid user on an admin route gets four oh three.
q3 | N | normal | Three. Four hundred versus four twenty two? Four hundred, the request could not be understood. Four twenty two, understood, but fails a business rule. A four hundred is usually a client bug. A four twenty two is usually a message to show the user.
q4 | N | normal | Four. Intermittent five oh twos and five oh fours from one endpoint. First check whether the upstream responds at all. Five oh four, it never answered in time, so check latency and health. Five oh two, it answered with something invalid, so check its raw response, or a crash mid response.
q5 | N | normal | Five. A trap. Is patch always non idempotent, and put always idempotent? No to both. A put is idempotent by definition, but a buggy one that appends to a log each time is not. A patch with absolute values is idempotent in practice, a relative one is not.
q6 | N | normal | Six. Why both secure and http only? They block different attacks. Secure stops sending over plain H T T P, where an observer could read it. Http only stops scripts reading it, so cross site scripting cannot exfiltrate it. Either alone is not enough.
q7 | N | normal | Seven. What does same site solve, and strict versus lax? It controls whether a cookie rides on a request that began on another site, the basis of cross site request forgery. Strict never sends it cross site, but breaks logging in from an emailed link. Lax, the modern default, allows top level navigation, not embedded requests.
== s17 Summary
s0 | N | calm | Let us put it all together, from easy to advanced.
s1a | N | normal | One. H T T P is a shared vocabulary. A request is a method, a path, headers, and an optional body. A response is a status code, headers, and an optional body. And it is stateless.
s1b | N | normal | Two. Safe means no state change. Idempotent means the same end state if repeated. Get, head, options are both. Put and delete are idempotent. Post is neither, and patch is usually not.
s1c | N | normal | Three. Status families. Two success, three redirect, four client error, five server error. Four oh one, who are you. Four oh three, you may not. Four hundred is malformed, four twenty two is invalid, four oh nine is a state conflict. Five oh two, bad answer. Five oh three, unavailable. Five oh four, too slow.
s1d | N | normal | Four. A few headers do most of the work. Host, content type, content length, authorization, cache control, E tag, cookies, and connection. E tag with if none match gives a three oh four, no body.
s1e | N | warn | Five. Cookies need all three. Secure stops sniffing. Http only stops script theft. Same site stops forged cross site requests.
s1f | N | normal | Six. Keep alive saves handshakes, not ordering. The semantics are the same in H T T P one, two and three. Only the wire format changed. And chunked transfer streams a body of unknown size.
s1g | N | calm | And the one line to keep. H T T P is asking with a method and a path, answering with a status code, and remembering nothing, unless a cookie or token carries it.
